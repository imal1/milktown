# 版本对比显示 Markdown 源码差异，并统一序列化风格

双页视图里的版本对比，显示的是**两个版本的 Markdown 源码行级差异**（增删按行标记，形式与 git 一致），而不是渲染后的富文本差异。

这是一条自觉的产品让步：milktown 是所见即所得编辑器，日常写作中用户从不接触源码，却在对比版本时被要求阅读源码。接受这一点，是因为渲染层差异的实现路径不可靠——`prosemirror-changeset` 需要的输入是编辑步骤而非文档快照，而从两份快照倒推步骤所需的 `prosemirror-recreate-steps` 主包已从 npm 消失，只余一个陈旧的第三方 fork。

## Considered Options

- **渲染后的字符级富文本差异** —— 产品上最优，实现路径不可靠，见上。
- **渲染后的块级差异**（在源码层计算，映射回渲染后的段落 / 标题 / 列表项整块标记）—— 曾被推荐，用户选择了源码级。若日后觉得源码 diff 太刺眼，这是现成的升级路径。

## 规范化是这条路的前提

所见即所得编辑器的「Markdown → 文档 → Markdown」往返**不保证字节一致**。若不处理，从别处带来的文件在 milktown 中原封不动地保存一次，就会产生一个「整个文件都变了」的差异，第一个版本就毁掉历史的可读性。

变化面远不止空行：无序列表标记、斜体与加粗的符号、代码围栏字符、分隔线写法、ATX 与 Setext 标题、有序列表编号是否递增、列表缩进宽度、表格对齐空格、链接是内联还是引用式、硬换行写法、文件末尾换行。

因此：

**基线时机** —— 打开文件时立即在**内存中**计算规范化文本，作为该文件所有差异计算的基线；**不写盘**。规范化结果直到用户第一次保存才落到磁盘。打开文件不应擅自改写用户的文件。

**序列化风格** —— 通过 Milkdown 的 `remarkStringifyOptionsCtx`（其内部使用 `remark-stringify` ^11）钉死为以下一套，整体对齐 Prettier 的 Markdown 默认值，以便文件被其他工具处理时冲突最小：

| 项 | 定为 |
| --- | --- |
| 无序列表标记 | `-` |
| 斜体 | `_x_` |
| 加粗 | `**x**` |
| 代码围栏 | 反引号 |
| 分隔线 | `---` |
| 标题 | ATX（`# 标题`） |
| 有序列表编号 | 递增（`1.` `2.` `3.`） |
| 块间空行 | 一个 |
| 文件末尾 | 一个换行 |

## Consequences

- 用户所有经 milktown 保存过的文件都会被统一成上述风格。这是不可逆的——文件已被改写。
- 差异计算发生在规范化文本之间，因此历史中不会出现纯格式噪音的版本。
- 若日后升级到块级或字符级的渲染层差异，规范化这一层仍然需要，不会白做。
